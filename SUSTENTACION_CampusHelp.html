1. Introducción

1.1 Descripción del Proyecto

CampusHelp es una aplicación web desarrollada en el marco del taller académico de ScrumBan que permite gestionar incidentes y solicitudes de servicios tecnológicos en una universidad. La aplicación cubre el flujo completo de atención: desde el registro de un incidente hasta su cierre, pasando por asignación, atención técnica y validación.

1.2 Objetivo General

Diseñar e implementar un sistema de mesa de ayuda (Help Desk) que permita a los usuarios reportar incidentes, a los agentes técnicos gestionar casos, y a los validadores confirmar la resolución, todo dentro de un flujo controlado con reglas de negocio estrictas.

1.3 Objetivos Específicos

  • Implementar un API REST robusta con validación de reglas de negocio en el backend
  • Desarrollar una interfaz web intuitiva que permita recorrer el flujo completo de atención
  • Garantizar la persistencia de datos en una base de datos relacional
  • Aplicar metodología ScrumBan con sprints iterativos y entregables incrementales
  • Validar el sistema mediante pruebas automatizadas (48 tests) y verificación funcional

2. Justificación del Proyecto

Las universidades enfrentan un volumen creciente de solicitudes de soporte técnico: desde problemas de conectividad hasta gestión de cuentas académicas. Sin un sistema centralizado, estas solicitudes se pierden, no se priorizan adecuadamente y no hay trazabilidad del servicio.

CampusHelp resuelve esta necesidad proporcionando:

  • Trazabilidad completa: cada cambio de estado queda registrado en un historial inmutable
  • Control de flujo: solo ciertas transiciones de estado son permitidas, evitando errores operativos
  • Roles y responsabilidades: cada rol tiene permisos específicos validados en el backend
  • Métricas e indicadores: el sistema genera estadísticas para la mejora continua del servicio
  • Principios ScrumBan: el tablero Kanban y los límites WIP permiten visualizar y optimizar el flujo de trabajo

4. Metodología — ScrumBan

4.1 ¿Qué es ScrumBan?

ScrumBan es una metodología híbrida que combina elementos de Scrum (sprints, roles, ceremonias) con Kanban (tablero visual, límites de trabajo en progreso, flujo continuo).

4.2 Implementación en CampusHelp

Sprints3 sprints incrementales con entregables definidos
RolesSolicitante, Agente, Validador, Administrador
Tablero KanbanFrontend con 5 columnas (Pendiente → Cerrada)
Límites WIPMáximo 3 casos en análisis/atención, 2 en validación
Flujo PullLos agentes "toman" casos de la bandeja disponible
Mejora continuaIndicadores y métricas para optimizar el servicio

4.3 Estructura de los Sprints

Sprint 1 — Fundamentos (Semana 1-2)

Objetivo: Establecer la base del sistema: base de datos, API REST básica, y primeras pantallas del frontend.

Backend:

  • Diseño y creación del esquema de base de datos (6 tablas: usuario, area, categoria, caso, historial, atencion)
  • Implementación del seed con datos de prueba (5 áreas, categorías, 4 usuarios por rol)
  • API REST: POST /api/casos (registro), GET /api/casos (bandeja), GET /api/areas, GET /api/categorias, GET /api/usuarios
  • Validaciones en backend: tipo, descripción (mín. 10 caracteres), prioridad, categoría activa
  • Historial automático al crear un caso
  • Pruebas automatizadas: 48 tests cubriendo endpoints, validaciones y flujo básico

Frontend:

  • Configuración del proyecto React + Vite + TypeScript + Tailwind
  • Formulario de registro de casos (HU-01)
  • Bandeja de casos con tablero Kanban (HU-02, HU-03)
  • Vista "Mis casos" para el rol solicitante (HU-02)
  • Integración con la API real (fetch HTTP)

Sprint 2 — Flujo de Atención (Semana 3-4)

Objetivo: Implementar el flujo completo de atención: asignación, atención técnica y validación.

Backend:

  • POST /api/casos/:id/asignar — asignación de agente (solo agentes, sin duplicados)
  • PATCH /api/casos/:id/estado — cambio de estado con validación de transiciones
  • POST /api/casos/:id/atencion — registro de diagnóstico y solución (solo agente asignado)
  • POST /api/casos/:id/validacion — aprobar o devolver (solo validadores)
  • Control estricto de transiciones: Pendiente → En análisis → En atención → En validación → Cerrada
  • Historial automático en cada cambio de estado (misma transacción)
  • Validación de permisos por rol en cada endpoint
  • Pruebas automatizadas para cada endpoint nuevo

Frontend:

  • Vista de detalle de caso con historial (HU-08)
  • Formulario de registro de diagnóstico y solución (HU-06)
  • Panel de validación con botones aprobar/devolver (HU-07)
  • Botones de cambio de estado según rol y estado actual (HU-05)
  • Asignación de agentes desde el detalle del caso (HU-04)

Sprint 3 — Métricas y Gestión (Semana 5-6)

Objetivo: Agregar indicadores, dashboard de métricas y gestión de categorías.

Backend:

  • GET /api/indicadores — métricas agregadas: casos por estado, por tipo, por prioridad, tiempos promedio
  • POST /api/categorias — crear categorías (solo administrador)
  • PATCH /api/categorias/:id — editar categorías
  • PATCH /api/categorias/:id/activar — activar/desactivar (no se puede desactivar si tiene casos)
  • Filtros combinables en GET /api/casos (estado, tipo, área, categoría, prioridad)
  • Pruebas automatizadas para los nuevos endpoints

Frontend:

  • Dashboard de indicadores con gráficas de barras (HU-10)
  • CRUD de categorías (HU-11)
  • Buscador con filtros combinados (HU-09)
  • Mejoras en UX: estados de carga, manejo de errores, feedback visual

5. Arquitectura del Sistema

5.1 Diagrama de Arquitectura

El sistema sigue una arquitectura de tres capas:

  • Capa de Presentación (Frontend): React + TypeScript + Tailwind CSS + Vite
  • Capa de Aplicación (Backend): Node.js + Express REST API
  • Capa de Datos (BD): PostgreSQL 16 con 6 tablas relacionales

5.2 Flujo de Datos

  1. El usuario interactúa con la interfaz React
  2. El frontend hace llamadas HTTP a la API REST (JSON)
  3. El backend procesa la solicitud, valida reglas de negocio y permisos
  4. El backend ejecuta consultas SQL parametrizadas a PostgreSQL
  5. Los datos persisten en la BD y se retorna la respuesta JSON
  6. El frontend actualiza la interfaz con la respuesta

6. Reglas de Negocio

6.1 Estados y Transiciones

El sistema tiene exactamente 5 estados:

  1. Pendiente — Caso registrado, sin asignar
  2. En análisis — Agente asignado, analizando el caso
  3. En atención — Trabajando en la resolución
  4. En validación — Solución registrada, pendiente de validación
  5. Cerrada — Caso validado y cerrado

Transiciones permitidas:

  • Pendiente → En análisis
  • En análisis → En atención
  • En atención → En validación
  • En validación → Cerrada (aprobar)
  • En validación → En atención (devolver)

Nota importante: "Devuelta" NO es un estado, es la transición En validación → En atención.

6.2 Reglas de Validación

  • Registro: tipo, categoría, título, descripción (mín. 10 caracteres) y prioridad son obligatorios
  • Estado inicial: Pendiente
  • Fecha de creación: automática (CURRENT_TIMESTAMP)
  • Solo el agente asignado puede registrar la atención
  • No se puede cerrar un caso sin solución registrada
  • Un caso Cerrado no puede modificarse
  • Cada cambio de estado genera un evento en el historial (misma transacción)
  • Los permisos por rol se validan en el backend
